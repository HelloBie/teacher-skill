# Stage 5: Final assessment

Load after the entire course syllabus has actually been taught. Base the assessment on the real syllabus, taught material and learning objectives; the learner chooses when to participate and can request changes, postponement or skipping it.

## Eligibility and exam design

1. Inspect the current syllabus, each lesson's teaching status, notes and summaries, real Q&A and progress. A plan, template or completed individual lesson does not mean the course is taught.
2. Once all material is taught, cover major modules and key abilities. Uncorrected old exercises do not automatically block participation or count as mastery. If material was skipped or untaught, offer to teach it according to the learner's preference; an explicitly requested early test must state omissions and be labeled a partial assessment, not a comprehensive final.
3. Build an assessment blueprint mapping modules or skills and taught lessons to question numbers, task types, points or evaluation criteria. Test taught content and reasonable integrated application; give background and data for cross-topic tasks and do not require untaught knowledge.
4. Choose questions appropriate to the subject: conceptual, true/false, multiple choice, short answer, scenario, practical project, performance or code. Do not require a programming question or fixed duration. Make scoring, weights and pass or capability criteria clear and allow multiple valid approaches when applicable.

## Files and paper

Follow an existing course layout; otherwise create an `exams/` folder when needed, with `README.md` for scope, version, blueprint, links, rules and actual status, and `exam_01.md` for complete questions, points or criteria, directions and answer spaces. Add separate answer files, case materials or code starters only if useful. Specify submission and review method, whether references are allowed, and appropriate observable outcomes; do not reveal solutions through sample outputs. State that this is a self-assessment whose reliability depends on coverage, conditions and verifiable evidence.

Before issuing, verify syllabus coverage, totals, assumptions, links and runnable materials. Publish criteria but do not prefill answers or disclose solutions before submission. A local file is not a security or confidentiality mechanism. Clearly state practical limitations that cannot be verified.

## Issue, review and record

1. Deliver the exam and answer locations. Update the exam entry and course progress as issued/awaiting answers; issuing does not mean completion or passing.
2. On submission or review request, preserve original answers, explanations and code; append per-question dated, numbered feedback with result, score or evaluation, evidence, reasoning and useful guidance. Use behavior-preserving code comments. Mark unanswered work unsubmitted and do not guess; acknowledge and fairly adjust for defective questions.
3. Apply the published criteria to summarize module results and overall score or capability assessment, strengths, gaps and evidence. Distinguish submitted, awaiting review, reviewed/needs work and passed. Never present self-testing as official certification or claim an unverified result.
4. If useful, add an aggregate feedback file in `exams/`, while keeping feedback beside each answer and preserving prior rounds. Do not reveal solutions for unanswered items. Update the course entry, exam index and progress with version, links, actual status and next action.
5. For a requested retake, use a new exam or answer version, preserving the earlier paper, answers and feedback. Let the learner control further study and retake timing.
